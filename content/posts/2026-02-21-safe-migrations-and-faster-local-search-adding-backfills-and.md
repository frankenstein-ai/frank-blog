What do you do when production rows violate new constraints and your "find nearby" search needs to scale from tens to thousands of queries per minute? In 2026-W08 we made two changes in Find Workers: a safe Alembic migration that backfills nullable columns and normalizes legacy values so upgrades won't fail, and a performance change that adds a GiST spatial index on workers.location to speed ST_DWithin queries used by the "find nearby professionals" flow.

Below I cover the problems we hit, the concrete changes we made, and the practices that kept our test suite green (3.6k+ tests) while making production safer and search faster.

## Highlights

- An Alembic migration that backfills columns and repairs rows that would break NOT NULL / CHECK constraints.
- A migration that creates a GiST index on workers.location and a matching SQLAlchemy model change to use PostGIS-aware types.
- Small ruff/formatting fixes to alembic files to keep migrations lint-clean.
- Tests: commit messages reference test counts around 3,684 → 3,689, and CI remained stable.
- Files touched: 
  - alembic/versions/e5f6a7b8c9d0_fix_nullable_and_constraint_safety.py
  - alembic/versions/h8i9j0k1l2m3_add_spatial_index_worker_location.py
  - src/find_workers/models/worker.py
  - alembic/env.py and several formatted migration files

## Problem detail

1. Legacy data blocking stricter schema
   - Over time the DB accumulated rows that don't meet newer assumptions: NULLs where columns later became NOT NULL, old enum values, and other inconsistencies. Running an Alembic migration that immediately adds NOT NULL or tight checks will fail against that historical data.
   - We needed migrations that detect and normalize legacy rows, backfill safe defaults, and then apply constraints with minimal risk and downtime.

2. Geo search performance
   - The "find nearby" flow uses ST_DWithin (or ST_Distance) to find workers within a radius. Without a spatial index, those queries do sequential scans and latency grows with table size.
   - Creating a GiST index on a PostGIS Point/Geography column lets Postgres use index-assisted spatial searches so ST_DWithin can avoid scanning every row.

## What we changed

- alembic/versions/e5f6a7b8c9d0_fix_nullable_and_constraint_safety.py
  - The migration runs explicit, idempotent UPDATE statements to set defaults for NULLs and fix legacy enum/constraint values, then applies NOT NULL / CHECK constraints.
  - It includes defensive checks so it succeeds on long-lived production DBs.

- alembic/versions/h8i9j0k1l2m3_add_spatial_index_worker_location.py
  - Creates a GiST index on workers.location to speed ST_DWithin queries.

- src/find_workers/models/worker.py
  - Made the location column PostGIS-aware so the column type matches the index (Geometry(Point, 4326) or Geography(Point, 4326) depending on how distances are computed).

- Housekeeping
  - Small ruff-style changes in alembic/env.py and formatting of large autogenerated migration files to make diffs easier to review.

### Example: safe backfill migration pattern

A robust sequence to add NOT NULL / stricter constraints:

1. Backfill rows idempotently.
2. Only after backfill, add NOT NULL or CHECK constraints.

Example migration:

```python
# alembic/versions/e5f6a7b8c9d0_fix_nullable_and_constraint_safety.py
from alembic import op

def upgrade():
    # Backfill phone_country to 'BR' where missing
    op.execute("UPDATE workers SET phone_country = 'BR' WHERE phone_country IS NULL")

    # Normalize verification_status to a known set
    op.execute(
        "UPDATE workers SET verification_status = 'pending' "
        "WHERE verification_status IS NULL "
        "OR verification_status NOT IN ('pending','approved','rejected')"
    )

    # Apply NOT NULL after backfill
    op.alter_column('workers', 'phone_country', nullable=False)
    op.alter_column('workers', 'verification_status', nullable=False)
```

The real migration has more defensive logging and checks so it can run safely multiple times and be audited during rollout.

### Example: adding a GiST spatial index migration

We create the index explicitly from a migration so rollbacks and diffs are clear:

```python
# alembic/versions/h8i9j0k1l2m3_add_spatial_index_worker_location.py
from alembic import op

revision = "h8i9j0k1l2m3"
down_revision = "<previous_revision>"

def upgrade():
    # Ensure PostGIS extension exists
    op.execute("CREATE EXTENSION IF NOT EXISTS postgis;")
    # Create a GiST index on workers.location
    op.execute("CREATE INDEX IF NOT EXISTS ix_workers_location_gist ON workers USING GIST (location);")

def downgrade():
    op.execute("DROP INDEX IF EXISTS ix_workers_location_gist;")
```

The index expects the location column to be a PostGIS geometry or geography type.

### SQLAlchemy model snippet (worker.location)

Make the model explicit so model code and migrations match:

```python
# src/find_workers/models/worker.py
from sqlalchemy import Column
from geoalchemy2.types import Geography
from sqlalchemy.dialects.postgresql import UUID

class Worker(Base):
    __tablename__ = "workers"
    id = Column(UUID(as_uuid=True), primary_key=True)
    # Use Geography(Point, 4326) if you want ST_DWithin/ST_Distance in meters.
    location = Column(Geography(geometry_type='POINT', srid=4326), nullable=True, index=False)
```

We don't set index=True here because we create the GiST index explicitly in Alembic.

### Example: the ST_DWithin query that benefits

We avoid computing distances for every row by using ST_DWithin:

```sql
SELECT id, name,
  ST_Distance(location::geography, ST_MakePoint(:lng, :lat)::geography) AS distance_m
FROM workers
WHERE ST_DWithin(location::geography, ST_MakePoint(:lng, :lat)::geography, :radius_m)
ORDER BY distance_m
LIMIT :n;
```

With a GiST index on location, Postgres can use an index-assisted plan and skip a full table scan, which keeps latency steady as the table grows.

## Alembic housekeeping / linting fixes

We simplified include_object and applied ruff formatting to reduce noise in diffs.

Before:

```python
def include_object(object, name, type_, reflected, compare_to):
    if type_ == "table" and name in EXCLUDE_TABLES:
        return False
    return True
```

After:

```python
def include_object(object, name, type_, reflected, compare_to):
    return not (type_ == "table" and name in EXCLUDE_TABLES)
```

Small style fixes like this make reviews faster and reduce accidental churn in migration files.

## Results and verification

- Two migrations, a model update, and formatting changes were merged.
- Local and CI test runs stayed green; commit messages reference test counts near 3,684 → 3,689.
- The GiST index gives substantial speedups for radius searches on tables with thousands of rows compared to seq scans. If you benchmark, expect much lower latency and more predictable resource use for ST_DWithin queries.

## Lessons learned and recommendations

- Backfill before constraining. Never deploy a NOT NULL or strict CHECK without shipping backfill logic first. Production databases carry history.
- Create spatial indexes in migrations. Explicit index creation avoids surprises from implicit indexes and gives you a clean rollback path.
- Keep alembic/env.py small and deterministic. Tiny, well-scoped changes reduce lint noise and make migration tests stable.
- Validate migrations against a realistic dataset before running on production. Create a staging DB with historical rows and run alembic upgrade to catch edge cases.
- Keep model and migration in sync. If the model uses geography but the index is created against a geometry type (or vice versa), Postgres may not use the index.

## Closing

Migrations are where production surprises happen. The two changes we shipped — defensive backfills for legacy rows and an explicit GiST index for nearby search — are small in code but reduce failed upgrades and make the "find nearby" experience much faster. If you add geospatial search to a service, treat PostGIS indexes as first-class citizens and design your migrations for the messy reality of production data.
