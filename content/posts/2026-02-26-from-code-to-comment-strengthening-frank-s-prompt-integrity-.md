## 1. what is Frank?

Frank is a lightweight Go command‑line tool that turns commit history into Hugo blog posts. It uses Cobra for the CLI and SQLite to remember which commits it has already processed.

The workflow is simple:

1. Pull the newest commits with `git log`.
2. Store the hash of the last processed commit in a small SQLite database (`.frank‑state.db`).
3. Group the commits by day or week, attach the full diffs and the README, then hand the bundle to a language model.
4. Turn the model’s answer back into a Hugo‑compatible Markdown file.
5. Commit the new post to the Hugo repository.

Frank can talk to any LLM provider you prefer – GitHub Models, OpenAI, Anthropic, OpenRouter, or a local Ollama instance. A reusable GitHub Actions workflow (`.github/workflows/generate-reusable.yaml`) pulls Frank from source, runs `frank generate`, and pushes the posts back.

In this post we’ll look at two commits from 2026‑W09 that tighten up two core parts of this pipeline: prompt safety and state persistence.

## 2. the problem - fabricated metrics

### 2.1 why it matters

When an LLM generates content, it can sometimes invent facts that aren’t in the source data. For a tool that claims to rewrite commit history into a blog post without human editing, those hallucinations can cause a few real issues:

* Readers see a post that cites made‑up numbers and lose trust.
* The blog could break policy or be sued for misinformation.
* Downstream tools that summarize or analyze the content may get wrong data.

Frank’s original prompt told the model to include “concrete examples and metrics from the source material.” That instruction left room for the model to pull a metric from its training data that happens to fit the context, so the risk was still there.

### 2.2 the core question

> **How can we ensure that a generated post contains only data that actually appears in the commits, diffs, or README?**

It isn’t enough to say “be factual”; the prompt must forbid inventing anything.

## 3. prompt engineering for factfulness

Frank embeds the prompt in its binary via `go:embed`. The text lives in `internal/prompts/blogposts.txt`:

```
You are a content writer for a developer blog.
Your job is to transform a set of git commits, patch diffs and the README
into a cohesive, Hugo‑compatible markdown post.

Rules:
- Write for developers and AI practitioners
- Lead with the problem or question, not the solution
- Only include facts, examples, and metrics that are directly evident in the provided commits, diffs, or README — never fabricate data, statistics, or quotes
- Use the code diffs to understand what was actually changed, not just the commit messages
- Use the project README for context about the project’s purpose and architecture
- Synthesize all commits in the period into a single coherent narrative
```

The third bullet replaces the ambiguous earlier rule. The language now says the model must not make up data.

### 3.1 the diff

```
@@
 Rules:
 - Write for developers and AI practitioners
 - Lead with the problem or question, not the solution
-- Include concrete examples and metrics from the source material
+- Only include facts, examples, and metrics that are directly evident in the provided commits, diffs, or README — never fabricate data, statistics, or quotes
 - Use the code diffs to understand what was actually changed, not just the commit messages
 - Use the project README for context about the project's purpose and architecture
 - Synthesize all commits in the period into a single coherent narrative
```

The change keeps the same spirit while tightening the instruction. When a sophisticated LLM tries to fill gaps, the prompt explicitly forces it to stop.

### 3.2 why the explicit constraint helps

* The last instruction in the prompt becomes the model’s final instruction, limiting what it can output.
* The rule sticks around even if we later add more system messages for formatting.
* People looking at the prompt can see the safety rule right away, so they don’t have to chase other docs.

These properties make monitoring and review easier.

## 4. maintaining state – the `.frank‑state.db` commit

The second commit is a pipeline‑state change that happens automatically after a successful generation. The database file is regenerated by Frank each run and looks like this:

```sql
CREATE TABLE IF NOT EXISTS state (
    id INTEGER PRIMARY KEY,
    last_processed_commit TEXT NOT NULL,
    last_processed_at DATETIME NOT NULL
);
```

After processing, `last_processed_commit` is set to the newest commit hash. Subsequent `frank generate` calls skip anything older than that hash. The operation is idempotent, so no duplicate posts are ever written.

### 4.1 why the commit is skipped in ci

The commit is marked with `[skip ci]`. That tells GitHub Actions to ignore the push so CI doesn’t restart. If CI were to run Frank again, the new `.frank‑state.db` would cause another run, leading to an infinite loop.

This pattern keeps the CI workflow simple: it treats `frank generate` as a pure output step and ignores infrastructure changes that are part of the tool itself.

## 5. broader impact for developers

### 5.1 prompt‑safe content generation

Someone might worry that a strict “never fabricate” rule would make posts bland. In reality, the model simply omits any metric that isn’t directly in the commit history or README. If a commit adds a 30 % performance improvement and that change is in a diff, the post can cite that. If the commit never mentions a metric, the post won’t.

So the trade‑off is a straightforward one: no made‑up numbers, but accurate ones when they exist.

### 5.2 state consistency and merging

For teams that run Frank locally and in CI, the tiny SQLite database guarantees that each commit gets a post exactly once. If a commit is missed, a developer can run `frank status update --commit <hash>` to re‑generate its post.

When the `.frank‑state.db` file is committed back to the repo, it becomes a living log of everything Frank has published. The file can be cherry‑picked or reverted if needed.

### 5.3 zero‑config or one‑liner hooks

Because the prompt now hardens the “no fabrication” rule and because the state is handled automatically, you can drop a simple GitHub Actions workflow into any Hugo repo and get fact‑based posts without inspecting the generated text. A minimal workflow looks like this:

```yaml
jobs:
  blog:
    uses: frankenstein‑ai/frank-blog-content‑creation/.github/workflows/generate-reusable.yaml@main
    secrets:
      gh‑pat: ${{ secrets.GH_PAT }}
```

Fine‑tune the PAT to have `repo` and `models:read` scopes and that’s it. If the workflow fails, reset the state file to the last good commit and run again.

## 6. going forward

### 6.1 quantifying fidelity

One idea is to add a validation pass that parses the Markdown output, pulls out every function or class name, and checks that those symbols are present in the diffs that Frank used. A test harness could automate that and surface any missed or invented data.

### 6.2 more granular prompt rules

For large projects it may be useful to narrow the prompt to a specific branch or tag. A rule like “only discuss changes in the `feature/X` branch” would keep the output tight and ensure the model doesn’t pull unrelated history.

### 6.3 community‑contributed skills

Frank already supports “skills” – small `.md` files that tweak the prompt or post‑process the output. With the “no fabrication” rule in place, contributors can write friendly phrasing or additional formatting without risk of injecting false statements. A small test suite can double‑check that the skill hasn’t broken the constraint.

## 7. takeaway

Frank is a small, self‑contained tool that sits beside a repo and turns its commit history into Hugo posts. In 2026‑W09 we made two concise changes:

1. **Prompt hardening** – the prompt now forbids fabricated data.
2. **State persistence** – the SQLite DB is committed with `[skip ci]` to keep CI quiet.

When you’re building an automated blog pipeline, the two habits that help avoid hallucination are:

* Put an explicit “never make up a fact” rule in the prompt.
* Store the last processed commit in a small, checked‑in database and avoid triggering CI on its updates.

Those steps don’t add big features, but they make the difference between a post that readers trust and one that spreads misinformation. If you’re planning to use an LLM to publish code‑history blogs, start with those two safeguards.
